# Iteration 5: Scalability and Performance

## Goal

**Achieve the scale and performance targets required for peak operations** - Enable horizontal scaling to handle peak season loads (10x normal, 10,000 orders/hour) while maintaining sub-2-second API response times for 95% of requests.

## Drivers Addressed

| Driver ID | Type | Description |
|-----------|------|-------------|
| **QA-01** | Quality Attribute (Primary) | **Scalability**: Given peak season where aggregate order volume across all warehouses reaches 10x normal load, when up to 10,000 replenishment orders per hour are submitted from store systems and picking confirmations are processed in parallel, then the WMS instance should handle the load with < 2 seconds average API response time for 95% of requests and scale horizontally without downtime. |
| **QA-05** | Quality Attribute | **Performance**: Given a warehouse operator performing operational tasks, when they search inventory or retrieve work queues (receiving, picking, packing), then screens must load within 1 second for 95% of interactive requests to avoid impacting operator productivity. |
| **AC-01** | Architectural Concern | **Cost-efficient scaling**: How to design the WMS as a cloud-native, scalable system that can handle large order volumes and peaks without excessive infrastructure cost. |

## Elements Refined

| Element | Current State | Refinement Needed | Related Driver |
|---------|---------------|-------------------|----------------|
| **WMS Application Container** | Single deployment per Kubernetes namespace | Refine to support **horizontal scaling** with multiple replicas, stateless design patterns, and session externalization | QA-01, AC-01 |
| **API Gateway** | Basic request routing and authentication | Refine to add **load balancing configuration**, request distribution across replicas, and rate limiting for burst protection | QA-01, QA-05 |
| **WMS Database (PostgreSQL)** | Single database per instance, no explicit partitioning | Refine with **table partitioning strategy**, indexing optimization, and connection pooling for high concurrency | QA-01, QA-05 |
| **Cache (Redis)** | Used for session and location capacity | Refine with comprehensive **caching strategy** for frequently accessed data (inventory, items, locations, work queues) | QA-05, QA-01 |
| **Message Broker** | Standard configuration for async messaging | Refine with **consumer scaling**, batch processing, and queue partitioning for high-throughput order processing | QA-01 |
| **Outbound Module** | Handles order intake, wave planning, picking | Refine internal components for **parallel processing** of orders and optimized allocation algorithms | QA-01 |
| **Inventory Module** | Handles inventory queries and updates | Refine with **read optimization** patterns for fast inventory searches and work queue retrieval | QA-05 |
| **Kubernetes Deployment** | Namespace isolation with resource quotas | Refine with **Horizontal Pod Autoscaler (HPA)** configuration and resource tuning | QA-01, AC-01 |

## Design Concepts Selected

| Design Concept | Pros | Cons | Discarded Alternatives |
|---|---|---|---|
| **Stateless Application Design** - Externalize all session state to Redis; no in-memory state between requests | Enables horizontal scaling without session affinity; any replica can handle any request; simplified failover; supports zero-downtime deployments | Increased latency for session retrieval (mitigated by Redis speed); requires careful design to avoid hidden state | **Sticky Sessions**: Limits load balancing effectiveness; complicates scaling; single point of failure per user session. **In-memory distributed cache (Hazelcast)**: Additional infrastructure complexity; JVM memory pressure |
| **Horizontal Pod Autoscaler (HPA)** - Kubernetes-native auto-scaling based on CPU, memory, and custom metrics | Automatic scaling based on actual load; cost-efficient (scale down during low traffic); native Kubernetes integration; supports custom metrics (orders/sec, queue depth) | Scaling latency (30-60 seconds to provision); requires proper resource requests/limits configuration; may over-provision during spiky loads | **Vertical Pod Autoscaler (VPA)**: Requires pod restart; limited scaling ceiling; not suitable for sudden load spikes. **Manual scaling**: Slow response to load changes; requires 24/7 operations; cost inefficient |
| **Database Connection Pooling with PgBouncer** - Connection pooler in transaction mode between application and PostgreSQL | Reduces database connection overhead; enables more application replicas than database connections; improves connection reuse; managed service available | Additional infrastructure component; slight latency overhead; transaction mode limitations with prepared statements | **Application-level pooling only (HikariCP)**: Each replica maintains connections; doesn't scale with many replicas; exhausts database connections. **No pooling**: Connection overhead per request; poor performance; connection limits hit quickly |
| **Table Partitioning (Range-based)** - Partition high-volume tables (inventory_transaction, order, picking_task) by date/month | Faster queries on recent data; efficient data archival; parallel query execution across partitions; maintenance operations on partitions | Increased query complexity for cross-partition queries; requires partition management automation; application must be partition-aware for optimal queries | **Sharding across databases**: Extreme complexity for a modular monolith; cross-shard queries problematic; overkill for single-warehouse instance. **No partitioning**: Query performance degrades with data growth; full table scans on large tables |
| **Database Read Replicas** - Asynchronous read replica for reporting and read-heavy queries | Offloads read traffic from primary; improves read scalability; enables reporting without impacting operations; managed service support | Replication lag (eventual consistency); routing complexity; not suitable for read-after-write scenarios | **Synchronous replication**: Higher write latency; reduced availability. **No read scaling**: Primary database becomes bottleneck for read-heavy workloads |
| **Cache-Aside Pattern with TTL** - Application manages cache explicitly; read-through with time-based expiration | Simple to implement; application controls cache consistency; works with any data store; selective caching of hot data | Cache misses hit database; potential for stale data within TTL; cache stampede risk on expiration | **Write-through cache**: Higher write latency; complexity for cache consistency. **Read-through with cache provider**: Less control over caching logic; vendor lock-in |
| **Multi-Level Caching (L1 Local + L2 Redis)** - In-process cache for static/reference data; Redis for shared mutable data | Minimal latency for reference data; reduces Redis calls; best of both approaches; configurable per data type | L1 invalidation complexity for mutable data; memory overhead in each replica; potential consistency issues | **Redis only**: Network round-trip for every cache access; higher latency for frequently accessed static data. **Local cache only**: Inconsistency across replicas; cache duplication; memory inefficient |
| **Competing Consumers Pattern** - Multiple consumer instances processing from same queue with acknowledgment | Linear scalability by adding consumers; automatic load distribution; fault-tolerant (failed consumer's messages reprocessed); native support in RabbitMQ/SQS | Message ordering not guaranteed; potential for duplicate processing (mitigated by idempotency); consumer coordination complexity | **Single consumer with threading**: Limited by single instance; no horizontal scaling; single point of failure. **Partitioned queues with dedicated consumers**: More complex; requires partition management; uneven load distribution |
| **Batch Processing for Order Intake** - Process orders in configurable batches (e.g., 100 orders) rather than individually | Reduced database round-trips; better throughput; amortizes transaction overhead; efficient for bulk operations | Increased latency for individual orders; batch failure affects multiple orders; more complex error handling | **Individual order processing**: Higher overhead per order; cannot meet 10,000/hour throughput. **Micro-batching with streaming**: More infrastructure complexity; overkill for order intake |
| **CQRS-Lite (Optimized Read Models)** - Separate optimized views/tables for read-heavy queries (inventory search, work queues) | Fast reads from denormalized views; write and read paths optimized independently; supports complex query patterns efficiently | Data duplication; eventual consistency between write model and read views; view maintenance overhead | **Full CQRS with Event Sourcing**: Excessive complexity; major architectural change; steep learning curve. **Single model with indexes only**: Limited optimization options; complex queries still slow |
| **Async Processing for Non-Critical Operations** - Move audit logging, analytics, notifications to async event handlers | Reduces request latency; improves throughput; failures don't block critical path; better resource utilization | Eventual consistency for async operations; more complex debugging; requires event infrastructure | **Synchronous processing for all**: Higher latency; reduced throughput; failures cascade. **Fire-and-forget**: No reliability guarantees; potential data loss |
| **Database Indexing Strategy** - Composite indexes on frequently queried columns; covering indexes for hot queries | Dramatic query performance improvement; supports QA-05 1-second target; relatively simple to implement | Index maintenance overhead on writes; storage overhead; requires query analysis to optimize | **No additional indexes**: Poor query performance; full table scans. **Index everything**: Write performance degradation; excessive storage |
| **API Response Compression (gzip)** - Compress API responses for large payloads | Reduced network transfer time; lower bandwidth costs; significant improvement for list responses | CPU overhead for compression; not beneficial for small payloads; client must support decompression | **No compression**: Higher latency for large responses; increased bandwidth costs. **Binary protocols (protobuf)**: Client compatibility issues; more complex debugging |

## Instantiation Decisions

| Instantiation Decision | Rationale |
|------------------------|-----------|
| **WMS Application configured as stateless** with session externalized to Redis and multiple replicas managed by HPA | Enables horizontal scaling without session affinity; any replica can handle any request; supports zero-downtime deployments; addresses QA-01 scaling requirement |
| **Horizontal Pod Autoscaler (HPA)** with custom metrics (orders/sec, CPU utilization) scaling from 2 to 10 replicas | Automatic scaling based on actual business load; cost-efficient scale-down during low traffic (AC-01); responds to peak loads within 30-60 seconds; supports 10x load requirement |
| **PgBouncer connection pooler** in transaction mode between WMS replicas and PostgreSQL | Enables more application replicas (10×20=200 connections) than database connections (100); prevents connection exhaustion during horizontal scaling; improves connection reuse |
| **PostgreSQL read replica** for reporting and dashboard queries | Offloads read traffic from primary database; enables concurrent report generation without impacting operational transactions; supports reporting requirements without performance degradation |
| **Table partitioning by date range** for high-volume tables (inventory_transaction, replenishment_order, picking_task, outbox_message, audit_log) | Faster queries on recent data; efficient data archival; parallel query execution; queries on current month partition avoid scanning historical data |
| **Optimized database indexes** on frequently queried columns (location+status, sku+status, status+due_date, status+priority) | Dramatic improvement for inventory search and work queue retrieval; supports QA-05 1-second target; index scans instead of table scans |
| **Multi-level caching** with Caffeine L1 (in-process) for reference data and Redis L2 (distributed) for mutable data | L1 provides sub-millisecond access for static data (items, locations); L2 provides shared cache for inventory and work queues; reduces database load by 80%+ for read operations |
| **Cache-Aside pattern with TTL-based expiration** and explicit invalidation on writes | Application controls cache consistency; TTL (10s-15min based on data type) ensures eventual refresh; explicit invalidation on writes maintains near real-time accuracy for critical data |
| **Batch order processing** with configurable batch sizes (100 orders per batch) | Reduces database round-trips; single INSERT for 100 orders vs 100 separate INSERTs; amortizes transaction overhead; achieves 3,000 orders/min throughput |
| **Competing consumers pattern** for message queue processing with auto-scaling consumers (1-5 replicas) | Linear scalability by adding consumers; handles 10,000+ messages/hour; fault-tolerant with automatic reprocessing; scales based on queue depth |
| **API response compression (gzip)** at API Gateway | Reduces response payload size by 70-80%; improves response time for large list responses; minimal CPU overhead |
| **KEDA integration** for event-driven autoscaling with custom metrics from Prometheus | Scales based on business metrics (orders/sec, queue depth) rather than just CPU; more responsive to actual workload patterns |

## Design Decisions

| Driver | Decision | Rationale | Discarded Alternatives |
|--------|----------|-----------|------------------------|
| QA-01: Horizontal scaling | Implement **Stateless Application Design** with all session state externalized to Redis | Enables horizontal scaling without session affinity; any WMS replica can handle any request; supports zero-downtime deployments; simplifies load balancing; replicas can be added/removed dynamically | **Sticky Sessions**: Limits load balancing effectiveness; single point of failure per user session; complicates scaling decisions; uneven load distribution. **In-memory distributed cache (Hazelcast/Infinispan)**: Additional infrastructure complexity; JVM memory pressure; cluster coordination overhead |
| QA-01: Auto-scaling | Deploy **Horizontal Pod Autoscaler (HPA)** with custom metrics (orders/second, CPU utilization) scaling WMS replicas from 2 to 10 | Automatic scaling based on actual business load; cost-efficient scale-down during low traffic periods (AC-01); responds to peak loads within 30-60 seconds; native Kubernetes integration; supports both resource and custom metrics | **Vertical Pod Autoscaler (VPA)**: Requires pod restart for scaling; limited scaling ceiling; not suitable for sudden load spikes; slower response time. **Manual scaling**: Slow response to load changes; requires 24/7 operations team; cost inefficient; cannot handle unexpected peaks |
| QA-01: Auto-scaling metrics | Integrate **KEDA (Kubernetes Event-Driven Autoscaling)** with Prometheus for custom metric-based scaling | Scales based on business metrics (orders/sec, queue depth) rather than just infrastructure metrics; more responsive to actual workload patterns; supports scaling to zero for cost savings; integrates with existing Prometheus monitoring | **HPA with CPU only**: Doesn't reflect business load accurately; may under/over-scale; reactive rather than predictive. **Custom autoscaler implementation**: Development and maintenance overhead; reinventing existing solutions |
| QA-01: Database connections | Deploy **PgBouncer connection pooler** in transaction mode between WMS replicas and PostgreSQL | Enables more application replicas (10x20=200 connections) than database connections (100); prevents connection exhaustion during horizontal scaling; improves connection reuse; reduces database connection overhead | **Application-level pooling only (HikariCP)**: Each replica maintains dedicated connections; doesn't scale with many replicas; exhausts database max_connections quickly. **No connection pooling**: Connection overhead per request; poor performance; hard connection limits hit immediately |
| QA-01, QA-05: Read scaling | Deploy **PostgreSQL read replica** with async replication for reporting and dashboard queries | Offloads read traffic from primary database; enables concurrent report generation without impacting operational transactions; improves read scalability; managed service handles replication complexity | **Synchronous replication**: Higher write latency; reduced availability during network issues; overkill for reporting use case. **No read scaling**: Primary database becomes bottleneck; reports compete with transactions; poor dashboard performance |
| QA-01: Database performance | Implement **Table Partitioning (range-based by date)** for high-volume tables: inventory_transaction (monthly), replenishment_order (monthly), picking_task (monthly), outbox_message (weekly), audit_log (monthly) | Faster queries on recent data without scanning historical partitions; efficient data archival and purging; parallel query execution across partitions; partition pruning reduces I/O; manageable maintenance windows per partition | **Sharding across databases**: Extreme complexity for modular monolith; cross-shard queries problematic; distributed transactions required; overkill for single-warehouse instance scale. **No partitioning**: Query performance degrades with data growth; full table scans on large tables; slow maintenance operations |
| QA-05: Query performance | Implement **Optimized Database Indexes** on frequently queried columns: inventory(location_id, status), inventory(sku, status), replenishment_order(status, due_date), picking_task(status, sequence_number) | Dramatic improvement for inventory search and work queue retrieval; supports QA-05 1-second target; index scans instead of table scans; composite indexes match query patterns; partial indexes reduce storage for filtered queries | **No additional indexes**: Poor query performance; full table scans; cannot meet QA-05 targets. **Index all columns**: Write performance degradation; excessive storage overhead; index maintenance during bulk operations |
| QA-05: Cache architecture | Implement **Multi-Level Caching** with Caffeine L1 (in-process, 5-15 min TTL) for reference data and Redis L2 (distributed, 10s-5 min TTL) for mutable data | L1 provides sub-millisecond access for static data (items, locations, UoM); L2 provides shared cache across replicas for inventory and work queues; reduces database load by 80%+ for read operations; appropriate TTL per data type balances freshness vs performance | **Redis only**: Network round-trip for every cache access; higher latency for frequently accessed static data; unnecessary load on Redis. **Local cache only**: Inconsistency across replicas for mutable data; cache duplication; no sharing of computed results |
| QA-05: Cache consistency | Implement **Cache-Aside Pattern with TTL-based expiration** and explicit invalidation on writes | Application controls cache consistency; TTL ensures eventual refresh even if invalidation missed; explicit invalidation on writes maintains near real-time accuracy for critical data; simple to understand and debug | **Write-through cache**: Higher write latency; complexity for cache consistency across replicas. **Read-through with cache provider**: Less control over caching logic; vendor lock-in; harder to customize per data type |
| QA-01: Order throughput | Implement **Batch Order Processing** with configurable batch sizes (100 orders per batch) | Reduces database round-trips from 100 to 1 per batch; amortizes transaction overhead; achieves 3,000 orders/min throughput; efficient for store systems submitting bulk orders; single INSERT statement for batch | **Individual order processing**: 100x more database round-trips; higher transaction overhead; cannot meet 10,000 orders/hour throughput. **Micro-batching with streaming**: More infrastructure complexity (Kafka Streams, Flink); overkill for order intake pattern |
| QA-01: Message throughput | Implement **Competing Consumers Pattern** with auto-scaling consumer replicas (1-5) based on queue depth | Linear scalability by adding consumers; automatic load distribution across consumers; fault-tolerant with message redelivery; native support in RabbitMQ/SQS; scales based on actual queue backlog | **Single consumer with threading**: Limited by single instance capacity; no horizontal scaling; single point of failure. **Partitioned queues with dedicated consumers**: More complex; requires partition key management; uneven load distribution; partition rebalancing overhead |
| QA-05: API performance | Enable **API Response Compression (gzip)** at API Gateway for responses larger than 1KB | Reduces response payload size by 70-80% for large list responses; improves response time especially for inventory searches returning many items; minimal CPU overhead at gateway; standard HTTP feature supported by all clients | **No compression**: Higher latency for large responses; increased bandwidth costs; slower screen loads for data-heavy views. **Application-level compression**: Duplicated effort across replicas; inconsistent implementation; better handled at gateway |
| QA-05: Read optimization | Implement **CQRS-Lite with Optimized Read Models** using materialized views for dashboard queries and denormalized cache entries for work queues | Fast reads from pre-computed views; write and read paths optimized independently; complex aggregations pre-calculated; reduces query complexity for common screens | **Full CQRS with Event Sourcing**: Excessive complexity for WMS requirements; major architectural change; steep learning curve; eventual consistency challenges. **Single model with complex queries**: Limited optimization options; complex joins slow down interactive screens |
| AC-01: Cost efficiency | Configure **Scale-to-minimum during off-peak hours** with HPA minReplicas=2 during business hours, scheduled scale-down to 2 replicas overnight | Reduces compute costs during low-traffic periods; maintains minimum availability for overnight operations; automated scheduling reduces operational burden; aligns resource usage with actual demand | **Fixed replica count**: Over-provisioned during low traffic; higher costs; no adaptation to demand patterns. **Scale to zero**: Cold start latency unacceptable; loss of cached data; connection pool warmup delay |
| QA-01, QA-05: Performance targets | Define **Performance Benchmarks** with P95 targets: order submission <200ms, inventory search <500ms, work queue <300ms, dashboard <1s, overall API <2s | Clear targets for development and testing; measurable SLAs for operations; enables performance regression detection; aligns with QA-01 and QA-05 requirements; P95 accounts for variance while excluding outliers | **Average-based targets**: Hides tail latency issues; doesn't reflect user experience for slower requests. **P99 targets**: Too aggressive for initial implementation; harder to achieve consistently; diminishing returns |
| QA-01: Connection management | Configure **Connection Pool Sizing**: PgBouncer (20 min, 100 max per instance), HikariCP (5 min, 20 max per replica), Redis (5 min, 20 max per replica) | Right-sized pools balance resource usage with concurrency needs; PgBouncer multiplexes replica connections; HikariCP handles local connection lifecycle; prevents connection starvation while avoiding waste | **Oversized pools**: Wasted database connections; memory overhead; false sense of capacity. **Undersized pools**: Connection contention under load; increased latency; request queuing |

## Analysis Results

| Driver | Analysis Result | Justification |
|--------|-----------------|---------------|
| **QA-01: Scalability** (10x load, 10,000 orders/hour, <2s response for 95% of requests) | **Satisfied** | Multiple complementary decisions address scalability: (1) **Stateless Application Design** enables horizontal scaling without constraints; (2) **HPA with custom metrics** provides automatic 2-10 replica scaling; (3) **KEDA integration** ensures scaling responds to business load (orders/sec); (4) **PgBouncer connection pooling** removes database connection bottleneck during scaling; (5) **Table partitioning** prevents query degradation at scale; (6) **Batch order processing** (100/batch) achieves 3,000 orders/min throughput exceeding the 167/min requirement; (7) **Competing consumers** (1-5 replicas) provide linear message processing scalability. The combination of these decisions enables handling 10x load with <2s response times. |
| **QA-05: Performance** (1-second screen load for 95% of interactive requests) | **Satisfied** | Comprehensive decisions address interactive performance: (1) **Multi-level caching** (Caffeine L1 + Redis L2) reduces database load by 80%+ with sub-millisecond L1 access for reference data; (2) **Optimized database indexes** on frequently queried columns (inventory by location/SKU, tasks by status) enable index scans instead of table scans; (3) **PostgreSQL read replica** offloads reporting queries from transactional primary; (4) **CQRS-Lite with read models** provides pre-computed views for dashboards; (5) **API compression** reduces payload transfer time by 70-80%; (6) **Performance benchmarks** (P95: inventory search <500ms, work queue <300ms, dashboard <1s) provide measurable targets aligned with QA-05. |
| **AC-01: Cost-efficient scaling** | **Satisfied** | Decisions specifically address cost efficiency: (1) **HPA auto-scaling** scales down to 2 replicas during low traffic, avoiding over-provisioning; (2) **KEDA event-driven scaling** responds to actual business metrics, not just CPU, preventing unnecessary scaling; (3) **Scale-to-minimum configuration** for off-peak hours reduces overnight compute costs; (4) **Read replica only for reporting** avoids synchronous replication cost for non-critical reads; (5) **Multi-level caching** reduces database load, potentially allowing smaller database instances; (6) **PgBouncer** enables efficient connection reuse, reducing database resource requirements. |
